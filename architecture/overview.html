ContextWho this is for

One server in a house, doing five jobs

Everything described here runs on a single computer called beeblebox, sitting in a home office on a domestic broadband line. It publishes a public blog, runs automations that outside AI assistants can call, provides a private gateway to several AI providers, hosts a handful of demonstration applications, and backs all of it up to cloud storage once a week.

That is a small estate. It is also a real one: it has paying-attention consequences when it breaks, irreplaceable data, external users, and a public attack surface. The purpose of modelling it is not ceremony — it is to be able to answer, quickly and without opening a terminal, three questions that a non-technical stakeholder actually asks.

  • What would we lose? Which information could not be recreated, and where does it live.
  • Who can reach this? For every running service, whether the whole internet can address it, only the owner's devices, or nothing outside the machine.
  • Why is it built this way? Which decision each piece of technology follows from, rather than an inventory of products.
Framing

This is a baseline description — the estate as it is, not as it should be. There is no target architecture here, so weaknesses are recorded as first-class Gaps rather than quietly omitted. An architecture description with no gaps is a marketing document.

AssessmentMetadata worth holding

Choosing what to model, and what to refuse

TOGAF's Content Metamodel is designed for enterprises with programme portfolios and organisational units. Applied whole to a one-server estate it produces impressive, empty tables — which is worse than not modelling at all, because it makes the description look maintained when it is not. The assessment below is therefore as much about exclusion as inclusion.

Refused, with reasons

Organisation Unit, Business Process, Value Stream, Contract, Work Package, Measure. Every one of these presumes a structure this estate does not have: there is one person, no process hand-offs, no contracts, no funded work packages, and no service levels anyone has agreed to. Modelling them would mean inventing them.

Location is demoted from an entity to an attribute. TOGAF treats it as core because enterprises span sites; here there are precisely two places — the house and other people's clouds — so a field carries it without a table.

Target architecture and Gap Analysis in the TOGAF sense. Formal gap analysis compares baseline against target. There is no target architecture, so gaps are recorded directly against the baseline instead. This is a deliberate deviation, not an omission.

ExtensionsThree additions to core

Where the standard needed extending

TOGAF explicitly permits metamodel extension. Three were added, each because a question kept being asked that the core vocabulary could not express.

ExposureTier — who can reach this at all

TOGAF has no first-class concept for reachability zoning. In this estate it is the single most consequential design decision and the one most easily got wrong: a service intended for one person, published to the internet, is the failure mode that matters. Every endpoint sits in exactly one tier, and that is also the fact a non-technical reader most needs.

Control — the safeguard, tied to its reason

Modelled as an entity rather than prose so each safeguard can be traced both to what it protects and to the principle it serves. That constraint is doing real work: an unattached control is a finding. A control tied to no principle is unexplained; a principle with no control is unenforced. The validator refuses both.

Gap — what is known to be wrong

With no target architecture to diff against, gaps attach directly to the baseline. Recording them as entities rather than a footnote means they appear in the same views as everything else, and cannot be quietly dropped when the description is presented.

Modelling discipline

Four invariants are enforced mechanically, not by review. Every ApplicationService must declare exactly one exposure tier. Every Capability must be realised by something. Every Control must both protect an asset and implement a principle. And every DataEntity marked irreplaceable must reach a store that is actually backed up — the one invariant whose violation destroys the estate, so it is checked rather than assumed.

The dependency that is easy to miss

Platform secrets include the key that encrypts every stored automation credential. Restore the workflow database without it and the restore succeeds — producing a database full of text nobody can ever read again. Modelling secrets as an irreplaceable data entity in their own right, rather than treating them as configuration, is what forces that file into the backup set.

Following one decision all the way down

The test of an architecture description is whether a claim at the top can be walked to something running at the bottom. Here is the estate's most consequential principle, traced end to end.

  • DriverNear-zero recurring cost
  • PrincipleNo inbound ports
  • GovernsCloudflare & Tailscale as ingress
  • Realised byOutbound tunnel connector
  • ServiceBlog, published
  • TierPublic, edge-enforced

Read the other way, the chain explains a rejection rather than a choice. Forwarding a port from the router would have been simpler and free, and it was refused — a residential network has no security team, and an open port is permanent attack surface protecting the whole house, not just the service behind it. The principle records that reasoning so the next person does not re-litigate it, or worse, quietly undo it.

The same walk works for data. Blog content is classified irreplaceable; it is persisted in a database whose backup method is a logical dump; that dump is protected by a weekly off-site copy and by a restore rehearsal, both of which implement the principle that recovery is tested rather than assumed. Each link is a row in the model, and the validator fails if any of them is missing.

What is wrong with it

All six gaps below are accepted rather than planned — they are understood, and the cost of fixing them currently exceeds the cost of living with them. Recording that judgement is the point.

The first two compound each other, and that is the honest headline: the estate can lose its only server without losing its data, but nothing would tell anyone it had happened.

CurrencyKeeping it true

Why this description should still be true next year

Architecture documents rot because nothing contradicts them when they drift. This one is held to the estate by three deliberate choices.

The model is the source, the document is the view. Entities and relationships live in version-controlled YAML beside the configuration they describe, in the same repository and the same commits. A change to the estate and a change to its description travel together or the difference is visible in review.

Conformance is machine-checked. A validator enforces referential integrity, relationship typing, and the four invariants. It does not check that the model matches reality — nothing can — but it does refuse the specific decay that makes architecture models useless: dangling references, unclassified endpoints, controls attached to nothing.

The plain-language explanation is part of the model. Every motivation and business entity carries a stakeholder-facing sentence as a required field, and the validator rejects it if missing. The non-technical narrative is therefore generated from the same rows as the technical one, and cannot drift from it at presentation time.

Its honest limit

None of this proves the model is accurate. A validator confirms the description is internally coherent, not that it still matches what is running — that gap closes only by re-deriving the model from the live estate, which today is a manual act. It is the most valuable next step, and it is not done.
