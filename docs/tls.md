# TLS certificates

Certificates are generated by `scripts/setup-certs.sh` (separate from deployment).

## Where this private CA applies

Only the **LAN HTTPS doors** use it: Caddy on `:8443`–`:8451` and `:9443`. Everything else is
terminated elsewhere, so there is no CA to trust:

- **Tailnet fronts** (`:8090`, `:8092`, `:8098`, `:8099`, `:8105`) are plain HTTP on loopback;
  Tailscale terminates TLS with its own certificate.
- **Public sites** (Funnel on `:443`, Cloudflare Tunnel for thelearningcto.com) use publicly
  trusted certificates issued by Tailscale or Cloudflare. Their edge rules are in
  [`cloudflare/README.md`](../cloudflare/README.md).

`./scripts/deploy-to-server.sh` regenerates the certs on the target with the hostname, `.local`
name, first LAN IP and deploy target as SANs (add more with `DEPLOY_CERT_EXTRA_SANS`).

## Why the browser says "unsafe"

1. **Untrusted CA** (most common) – The CA that signed the server cert is not in your system’s trust store. Add `certs/ca.pem` as a trusted root (see table below).
2. **Name mismatch** – The host in the URL is not in the cert. Use `https://127.0.0.1:8443`, `https://localhost:8443`, or the hostname/IP from setup-certs.

## Generate certs (once per host)

```bash
./scripts/setup-certs.sh
# Or with hostnames: ./scripts/setup-certs.sh <hostname> <lan-ip>
```

**For a server host + your public domain:**
```bash
./scripts/setup-certs.sh <hostname> thelearningcto.com <hostname>.thelearningcto.com www.thelearningcto.com <lan-ip>
```

Then restart Caddy: `./scripts/start-stack.sh tls-proxy restart`. A cert or `Caddyfile` change
needs a restart, not `caddy reload`: after an rsync the bind-mounted file is a new inode and a
reload re-reads the stale one (see [ADD-SERVICE.md](ADD-SERVICE.md)).

Creates `certs/ca.pem`, `certs/server.pem`, `certs/server-key.pem`.

## Trust CA on clients

Browsers use the system trust store. Add `certs/ca.pem` to the **machine you browse from** before visiting the HTTPS URLs. Copy it from the server if needed: `scp <hostname>:~/localserver-config/certs/ca.pem .`

| OS | Command |
|----|---------|
| Linux | `sudo cp certs/ca.pem /usr/local/share/ca-certificates/localserver.crt && sudo update-ca-certificates` |
| macOS | `sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain certs/ca.pem` |
| Windows | See below |

**Windows (Chrome/Edge on same machine as WSL):** The Windows browser needs the CA trusted. From WSL, `certs/ca.pem` is at e.g. `~/localserver-config/certs/ca.pem`. In Windows Explorer, open `\\wsl$\Ubuntu\home\<user>\dev\localserver-config\certs\` (adjust distro/path) and copy `ca.pem` to your Desktop. Then: press Win+R → `certmgr.msc` → Trusted Root Certification Authorities → Certificates → right‑click → All Tasks → Import → select `ca.pem` → place in "Trusted Root Certification Authorities" → Finish. Restart the browser. (Firefox: Settings → Privacy & Security → Certificates → Import → select ca.pem.)

**Browser-specific:** Chrome and Edge use the OS trust store. Firefox uses its own.

## Troubleshooting

**HTTPS not working** – run on the server:
```bash
./scripts/check-tls.sh
```

| Check | Possible cause |
|-------|-----------------|
| Caddy not running | `./scripts/start-stack.sh tls-proxy up` |
| No certs | Run `./scripts/setup-certs.sh` first |
| Cert mismatch | Access using the IP or hostname in the cert (run setup-certs with that value) |
| Connection refused | Firewall blocking the Caddy ports (`8443`–`8451`, `9443`); open them, or on Windows see [NETWORK-CONFIG.md](NETWORK-CONFIG.md) and `scripts/setup-windows-podman-lan-ports.ps1` |
| Cert invalid / untrusted | Trust `certs/ca.pem` on the client (see table above) |
| Windows browser + WSL same machine | Import `certs/ca.pem` into Windows Trusted Root CAs (see Windows section above) |
| ERR_SSL_PROTOCOL_ERROR | Use `https://` not `http://`; try `https://127.0.0.1:8443` (IPv4) instead of localhost; ensure Caddy is running; from Windows try WSL IP: run `hostname -I` in WSL and use that IP |
| Server hostname doesn't resolve | Add a DNS record (for example Route53): `<hostname>.<your-domain>` → the server's LAN IP. Or add to hosts: `<lan-ip> <hostname> <hostname>.<your-domain>` |
| Hostname and IP both fail on Windows browser (WSL host) | **Simplest (same machine)**: Add `127.0.0.1 <hostname> <hostname>.<your-domain>` to the Windows hosts file. Run `scripts/setup-windows-hosts.ps1` as Admin. **Port forward**: Run `scripts/setup-windows-port-forward.ps1` as Admin. |
